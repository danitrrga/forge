# How the agent system works (read before changing config)

You are a coding agent (Claude Code or Codex) working in a project that **forge** manages. forge is a
checkout on this machine (the banner above names its path) that generates every managed project's agent
configuration from one source. Read the relevant section **before** you touch MCP servers, skills, plugins,
secrets, memory or hooks.

> **The one rule:** the forge checkout is the single source of truth for agent config. You change config by
> editing the **source files in forge**, then running a generator. You do **not** hand-edit generated files:
> they are overwritten, so a hand edit is lost on the next SessionStart.

This file is a synced copy (`.claude/AGENT-SYSTEM.md` in each project, git-ignored). The canonical one is
`docs/AGENT-SYSTEM.md` in forge; edit that, then run `python3 scripts/sync/sync_system_doc.py --apply`.

## Never hand-edit these

- `~/.claude.json`: MCP servers, project keys and enable flags.
- Any project's `.claude/settings.local.json`: plugin and skill on/off, permissions, env.
- The hook rows forge wrote into `~/.claude/settings.json` (its other keys are yours).
- With Codex on: `~/.codex/hooks.json`, a project's `.codex/config.toml` and its `.agents/skills` links.
- Any `.claude/AGENT-SYSTEM.md`, which is this synced copy.

In-session skill toggles, `claude mcp add` and manual JSON edits to those files are wiped on the next
SessionStart. If a change has to persist, make it in forge.

`.mcp.json` is **not** generated by anything. A project's own `.mcp.json` is the project's to maintain, and no
generator will correct it. If forge declares a server (in the registry and a profile), delete the project's
duplicate entry and let the profile own it.

## "I want to change X": edit Y, run Z

Paths are under the forge checkout. After any edit, run the generator as a dry-run first (it prints what would
change), then with `--apply`, and restart the affected session.

| Goal | Edit | Then run |
|---|---|---|
| Give a project an MCP server | add the server to `config/mcp-registry.json` if it is new, and list it in the project's profile under `servers` | `python3 bin/forge sync --apply` |
| Add or rotate a secret | `credentials/secrets.json` (git-ignored, the only place a real token lives; `config/secrets.json` links to it). The registry refers to it as `${VAR}` | `python3 bin/forge sync --apply` |
| Keep a skill or a plugin in a project | add its name to the profile's `skills_keep` or `plugins_keep` | `python3 bin/forge sync --apply` |
| Add a managed project | `python3 bin/forge add <path>`, which writes `config/profiles/<name>.claude.json` | (`add` runs the sync for it) |
| Add or edit a skill | `skills/<name>/SKILL.md` in forge; forge links it into `~/.claude/skills` | `python3 bin/forge sync --apply` |
| Add a skill to one project only | `<project>/.claude/skills/<name>/SKILL.md`. Claude Code reads it directly; for Codex forge mirrors it into `<project>/.agents/skills/<name>` | `python3 bin/forge sync --apply` |
| Add a hook for every session | a row in `user_hooks` in `config/forge.json` (forge writes `~/.claude/settings.json`, and `~/.codex/hooks.json` for a row that lists `codex`) | `python3 bin/forge sync --apply --all` |
| Add a hook for one project | the project's own `.claude/settings.json`, which forge never touches; use an absolute path and the interpreter for the file (`python3`, `node`, `bash`) | restart the session |
| Switch an integration on or off | `integrations` in `config/forge.json` | `python3 bin/forge sync --apply --all` |
| Edit this document | `docs/AGENT-SYSTEM.md` in forge | `python3 scripts/sync/sync_system_doc.py --apply` |

`forge sync` without `--apply` changes nothing. `--project NAME` limits it to one project and writes no
user-scope file; `--all` runs every project even from inside a session.

## Profiles: what each project loads

A profile is `config/profiles/<name>.claude.json`. Its fields and their types are `PROFILE_FIELDS` in
`forge/lib.py`. The parts that decide what a session sees:

- **`servers`**: the registry entries this project gets, written under its key in `~/.claude.json`.
- **`skills_keep`**: skills are user-global in Claude Code, so a profile with this list sets every other global
  skill `"off"` in `settings.local.json` (the project's own `.claude/skills` stay on). `["*"]` keeps all of them.
  A skill left out is switched off again on every restart, so never rely on an in-session toggle.
- **`plugins_keep`**: the same allowlist for plugins. A plugin installed later is off until it is listed.
- **`env`, `permissions`, `hooks`**: copied into the project's `settings.local.json`.
- **`writes_tracked_files: false`**: forge writes no file that git tracks in the project (its `CLAUDE.md`,
  `AGENTS.md`, `.gitignore`). The project's own instruction files then belong to the project.
- **`frozen: true`**: forge writes nothing in the project at all.

## Optional integrations

Codex, GSD, Jev, Hindsight and caveman are switches in `config/forge.json`. An integration that is off prints
`SKIP ... NOT RUN, NOT ARMED` in `forge doctor`, and forge removes only the entries it wrote for it.

## Checking the system

- `python3 bin/forge doctor` prints one line per check. `forge doctor NAME` limits it to one project.
- A `SKIP ... NOT RUN, NOT ARMED` line means the check had nothing to look at; it is neither a pass nor a
  failure. A `FAIL` names the command that fixes it.
- `python3 bin/forge test` runs the suites. Anything that writes is tested in a toy HOME, never in the real one.

## Secrets

Never read, print or copy a value from `credentials/` or from a generated `.mcp.json`, and never put a real token
in a file git tracks. If a token has to change, edit `credentials/secrets.json` and run the sync without
showing the value.
