# Closing a phase

You do these six steps in this order, after the last part's review. There is no closing conversation: the reports are written and the owner has read them. `<branch>` is the phase branch; `<default>` is `project.default_branch` of `.claude/fwx.json`. A step that fails is reported with its one-line reason and the phase stays open (no `closed` row yet): run this file again from step 1, because each step prints something recognisable when it is already done.

1. **Commit.** List the agents you launched that still run and stop those that work in the phase worktree: nothing may write to it from here on. Then commit `.fwx/` (rule 4 of `SKILL.md`; it prints `nothing to commit in <folder>` when that is done). With a protected default branch this is a commit on the phase branch, so the pull request carries the documents; without one it is a commit on the main checkout's branch, local, and the pull request does not carry it.
2. **Land.**
   - With `origin` on GitHub: `git push origin <branch>` from the worktree (`Everything up-to-date` when it is done), then the pull request: `gh pr view <branch>` exits 0 when it exists (open no other), else `gh pr create --base <default>` with a body of four sections, `## Why`, `## What changed`, `## Scope` (what the phase left out: `not_built` and `later` of `plan.md`) and `## Verification` (the evidence line of the last report: commit, command, exit code). For a job retaken from the factory the pull request already exists against the factory branch: the push updates it and you open no other.
   - Without `origin`: the branch stays where it is. Give the owner the command that merges it into `<default>`, as one line to paste, and do not run it: merging into the default branch is his.
   - Never push to `<default>` or to a branch in `production.branches`, because a merge there ships to users without his review. A deploy (`production.commands`) is run only through the consent window, which asks him: a "no" is reported once and not retried, because the owner has refused it. A push that fails is reported with git's message and you stop: a force push could discard work on the remote.
3. **A retaken job.** For an issue taken from Linear, ask "close `<KEY>` when this merges?". On yes, `Fixes <KEY>` goes in the pull request body (an existing one: append it with `gh pr edit`): Linear then moves the issue when the owner merges, and the client cannot edit issues. Then post the summary and the pull request link: `fwx linear comment <KEY> --kind result`, body on stdin.
4. **Stage.** Only when steps 1 and 2 succeeded (with no `origin`, when step 1 did): `fwx stage <phase folder> closed`, then commit `.fwx/` again (rule 4 of `SKILL.md`) and, with a protected default branch and an `origin`, `git push origin <branch>` again, so that the pull request carries the closed phase. If that last push fails the phase is closed and its commit is local: say so with git's message, and the owner pushes the branch.
5. **Cleanup.** After a UI walk, run `fwx walk sweep`. Run `git worktree list` and read the paths from it. Remove only this session's phase worktree, with `git worktree remove <path>` and no force (a forced removal discards uncommitted work), and only when its branch is on the remote (`git ls-remote --exit-code --heads origin <branch>` exits 0) and `git -C <path> status --porcelain` prints nothing: otherwise it holds work that exists nowhere else. Say which worktree you removed or kept and why, and how many belong to other sessions.
6. **Next.** When `fwx state list --json` shows no open phase in the milestone, say in one line what could come next: a new milestone or the next topic. Otherwise say nothing.
